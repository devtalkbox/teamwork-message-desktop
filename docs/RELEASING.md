# macOS Release Guide

The public GitHub release is distributed outside the Mac App Store. It must
use a **Developer ID Application** certificate, hardened runtime, Apple
notarization, and a stapled notarization ticket.

## One-time Apple setup

1. Join the Apple Developer Program with a two-factor-authenticated Apple
   Account.
2. In Certificates, Identifiers & Profiles, create a **Developer ID
   Application** certificate from a CSR generated by Keychain Access.
3. Install the downloaded certificate, then export the certificate and its
   private key from Keychain Access as a password-protected `.p12` file.
4. In App Store Connect, open **Users and Access → Integrations → Keys**.
5. Create a Team API key, download its `.p8` file, and record the Key ID and
   Issuer ID. The private key can only be downloaded once.

Never commit certificates, API keys, passwords, or encoded certificate files.

## GitHub environments

In the GitHub repository, open **Settings → Environments** and create two
environments, `staging` and `production`. Each one holds **its own** signing
certificate and notarization key, so a staging build can never be signed with
the production identity (or the other way round).

The workflow selects one of them with its `channel` input. That choice does two
things: it uses that environment's credentials, and it sets the server the
packaged app talks to. `buildEnvironment=staging` loads
`https://teamwork.staging.talkbox.net/m/`; `buildEnvironment=production` loads
`https://teamwork.gtomato.com/`.

Add these environment secrets to **both** environments:

| Secret | Value |
| --- | --- |
| `CSC_LINK` | Base64-encoded Developer ID Application `.p12` |
| `CSC_KEY_PASSWORD` | Password used when exporting the `.p12` |
| `APPLE_API_KEY` | Base64-encoded complete App Store Connect `.p8` file |
| `APPLE_API_KEY_ID` | App Store Connect API Key ID |
| `APPLE_API_ISSUER` | App Store Connect API Issuer ID |

Encode each credential as a single line on macOS:

```bash
openssl base64 -A -in DeveloperIDApplication.p12 -out certificate-base64.txt
openssl base64 -A -in AuthKey_XXXXXXXXXX.p8 -out apple-api-key-base64.txt
```

Copy the complete contents into the corresponding GitHub secrets, then
securely delete both encoded temporary files. For additional release control,
configure required reviewers on the `staging` environment.

Store these values under **Environment secrets**, not **Environment
variables**.

The workflow decodes `APPLE_API_KEY` into a private temporary `.p8` file with
mode `0600`. It removes the file immediately after notarization, including
when notarization fails. electron-builder handles the signing certificate from
`CSC_LINK`.

## Release channels

A release is built for exactly one channel. The channel is baked into the
package, so a staging build always opens the staging server and a production
build always opens production.

| | Production | Staging |
| --- | --- | --- |
| Trigger | push a `v<version>` tag | **Actions → Release macOS → Run workflow** |
| Channel input | (tag pushes default to production) | `staging` |
| Tag | `v5.2.0` | `v5.2.0-staging.1` |
| Artifacts | `Teamwork-5.2.0-<arch>.dmg` | `Teamwork-5.2.0-staging-<arch>.dmg` |
| GitHub Release | draft, reviewed before publishing | published immediately as a pre-release |

The tag check enforces the pairing: a production build rejects a tag ending in
`-staging.<n>`, and a staging build rejects a tag without it. Staging tags are
excluded from the tag trigger on purpose, so pushing one does not start a
production build.

For manual runs the workflow checks out the tag you name, so push it first:

```bash
git tag v5.2.0-staging.1
git push origin v5.2.0-staging.1
```

Production keeps the existing flow below; `yarn release:tag` builds the next
patch version and its tag.

## Publish a release

Before compiling, CI runs a read-only `notarytool history` request to verify
Apple authentication. A 401 requires checking the actual credentials in
App Store Connect; code cannot repair a revoked or mismatched key.
`APPLE_API_KEY` and `APPLE_API_KEY_ID` must refer to the same key.
For Team Keys, `APPLE_API_ISSUER` is the Issuer UUID, not the Team ID.
For Individual API Keys, set the `staging` environment **variable**
`APPLE_API_KEY_TYPE=individual` and use Xcode 26 or newer. The script omits
Issuer ID in this mode, as required by Apple. The default is `team`.
Private keys are validated as P-256 keys before contacting Apple.

1. Merge the intended release commit into the release branch and make sure the
   `main` working tree is clean.
2. Create the version commit and matching tag. `patch` is the default; `minor`,
   `major`, or an explicit `X.Y.Z` version can also be supplied:

   ```bash
   yarn release:tag
   yarn release:tag minor
   yarn release:tag 6.0.0
   ```

3. Review the generated version commit and tag, then push both:

   ```bash
   git push origin HEAD --follow-tags
   ```

4. The `Release macOS` workflow builds arm64 and x64 DMG/ZIP artifacts, signs
   them, submits each app to Apple, validates the stapled tickets, generates
   `SHA256SUMS.txt`, and creates a **draft** GitHub Release.
5. Download and smoke-test both DMGs from the draft. Publish the draft only
   after both packages pass.

The workflow intentionally fails when signing or notarization credentials are
missing. It also rejects a tag that does not exactly match the package version.

## Local credential validation

For a local release build, keep the `.p8` and `.p12` files outside the Git
repository and configure `.env` at the repository root:

```dotenv
CSC_LINK=/absolute/path/to/DeveloperIDApplication.p12
CSC_KEY_PASSWORD=your-p12-export-password
APPLE_API_KEY_PATH=/absolute/path/to/AuthKey_XXXXXXXXXX.p8
APPLE_API_KEY_ID=XXXXXXXXXX
APPLE_API_ISSUER=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
REQUIRE_NOTARIZATION=true
```

Do not set `APPLE_API_KEY` when `APPLE_API_KEY_PATH` is set. Validate the API
key with Apple's notary tool before the first CI release:

```bash
xcrun notarytool store-credentials "teamwork-notary" \
  --key "/absolute/path/to/AuthKey_XXXXXXXXXX.p8" \
  --key-id "XXXXXXXXXX" \
  --issuer "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
```

## Manual verification

```bash
codesign --verify --deep --strict --verbose=2 "Teamwork Wrap+.app"
spctl --assess --type execute --verbose=4 "Teamwork Wrap+.app"
xcrun stapler validate "Teamwork Wrap+.app"
```

The release workflow lives at `.github/workflows/release-macos.yml` and the
production builder configuration is `electron-builder.release.yml`.
