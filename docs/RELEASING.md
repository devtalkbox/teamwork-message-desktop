# macOS Release Guide

The public GitHub release is distributed outside the Mac App Store. It must
use a **Developer ID Application** certificate, hardened runtime, Apple
notarization, and a stapled notarization ticket.

## One-time Apple setup

1. Join the Apple Developer Program with a two-factor-authenticated Apple
   Account.
2. In Certificates, Identifiers & Profiles, create a **Developer ID
   Application** certificate from a CSR generated by Keychain Access.
3. Install the downloaded certificate, then export the certificate and its
   private key from Keychain Access as a password-protected `.p12` file.
4. In App Store Connect, open **Users and Access → Integrations → Keys**.
5. Create a Team API key, download its `.p8` file, and record the Key ID and
   Issuer ID. The private key can only be downloaded once.

Never commit certificates, API keys, passwords, or encoded certificate files.

## GitHub production secrets

In the GitHub repository, open **Settings → Environments → production** and
create the environment. Add these environment secrets:

| Secret | Value |
| --- | --- |
| `MAC_CSC_LINK` | Base64-encoded Developer ID Application `.p12` |
| `MAC_CSC_KEY_PASSWORD` | Password used when exporting the `.p12` |
| `APPLE_API_KEY` | Base64-encoded complete App Store Connect `.p8` file |
| `APPLE_API_KEY_ID` | App Store Connect API Key ID |
| `APPLE_API_ISSUER` | App Store Connect API Issuer ID |

Encode each credential as a single line on macOS:

```bash
openssl base64 -A -in DeveloperIDApplication.p12 -out certificate-base64.txt
openssl base64 -A -in AuthKey_XXXXXXXXXX.p8 -out apple-api-key-base64.txt
```

Copy the complete contents into the corresponding GitHub secrets, then
securely delete both encoded temporary files. For additional release control,
configure required reviewers on the `production` environment.

The workflow decodes `APPLE_API_KEY` into a private temporary `.p8` file with
mode `0600`. It removes the file immediately after notarization, including
when notarization fails. electron-builder handles the signing certificate from
`MAC_CSC_LINK`.

## Publish a release

1. Merge the intended release commit into the release branch.
2. Update `package.json` to the new version, for example `5.1.2`, and commit it.
3. Create and push an exactly matching tag:

   ```bash
   git tag v5.1.2
   git push origin v5.1.2
   ```

4. The `Release macOS` workflow builds arm64 and x64 DMG/ZIP artifacts, signs
   them, submits each app to Apple, validates the stapled tickets, generates
   `SHA256SUMS.txt`, and creates a **draft** GitHub Release.
5. Download and smoke-test both DMGs from the draft. Publish the draft only
   after both packages pass.

The workflow intentionally fails when signing or notarization credentials are
missing. It also rejects a tag that does not exactly match the package version.

## Local credential validation

For a local release build, keep the `.p8` and `.p12` files outside the Git
repository and configure `.env` at the repository root:

```dotenv
CSC_LINK=/absolute/path/to/DeveloperIDApplication.p12
CSC_KEY_PASSWORD=your-p12-export-password
APPLE_API_KEY_PATH=/absolute/path/to/AuthKey_XXXXXXXXXX.p8
APPLE_API_KEY_ID=XXXXXXXXXX
APPLE_API_ISSUER=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
REQUIRE_NOTARIZATION=true
```

Do not set `APPLE_API_KEY` when `APPLE_API_KEY_PATH` is set. Validate the API
key with Apple's notary tool before the first CI release:

```bash
xcrun notarytool store-credentials "teamwork-notary" \
  --key "/absolute/path/to/AuthKey_XXXXXXXXXX.p8" \
  --key-id "XXXXXXXXXX" \
  --issuer "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
```

## Manual verification

```bash
codesign --verify --deep --strict --verbose=2 "Teamwork Wrap+.app"
spctl --assess --type execute --verbose=4 "Teamwork Wrap+.app"
xcrun stapler validate "Teamwork Wrap+.app"
```

The release workflow lives at `.github/workflows/release-macos.yml` and the
production builder configuration is `electron-builder.release.yml`.
